# ADR: распределённое хранение submissions

Статус: **ЧЕРНОВИК** · владелец: №1

Документ разделяет три вида утверждений: **решено в контракте**, **предложение** (можно реализовать, но не согласовано) и **открытый вопрос** (нельзя придумывать без преподавателя).

1. Решено в контракте команды

- Два PostgreSQL-узла: `postgres_shard_0`, `postgres_shard_1`.
- Ключ распределения — `contestId`; все данные одного соревнования лежат на одном шарде.
- Каждая отправка защищена `fencing_token`: запись результата выполняется только при совпадении `submission_id` и актуального `fencing_token` (`stale_token` в остальных случаях).

2. Почему распределение по `contestId`

- Все таблицы соревнования (`teams`, `problems`, `submissions`, `idempotency_keys`, `outbox_events`, `standings`) на одном шарде, поэтому внешние ключи и транзакции «Submission + Outbox» остаются локальными, без распределённых транзакций.
- Standings считается по данным одного соревнования, без обращения к другому шарду.
- Минус: один очень большой контест не размазывается по узлам (горячий шард).

3. Consistent hashing с virtual nodes (предложение)

Реализация: `services/storage/src/storage/shard_router/ring.py`.

- Физические узлы: `postgres_shard_0`, `postgres_shard_1`. Каждый получает 128 виртуальных узлов на кольце.
- Позиция вычисляется как первые 8 байт SHA-256 строки; для узла `"<имя>#<номер>"`, для ключа `str(contest_id)`.
- Владелец ключа — первый виртуальный узел по часовой стрелке.
- Проверка на 20 000 случайных UUID дала распределение примерно 55% / 45%.
- Преимущество перед `hash % 2`: при добавлении узла перемещается лишь часть ключей, а не почти все.


4. Fencing token

Что уже есть: токен **на уровне отправки**. `claim` увеличивает `fencing_token`, а `write_result` содержит условие `WHERE submission_id = :id AND fencing_token = :token`. Проверка происходит в SQL, внутри транзакции записи результата, поэтому старый worker не может перезаписать новый результат. Это защищает от гонок между workerами.



7. Ограничения текущего решения

- Нет репликации и автоматического failover.
- Перенос соревнования между шардами при изменении кольца не реализован: данные нужно перемещать вручную.
- `GET /submissions/{submissionId}` не содержит `contestId`, поэтому шард по нему не определить: нужно либо опрашивать оба шарда, либо добавить `contestId` в путь или хранить отдельную карту `submissionId → contestId`. Это требует решения до реализации API.
