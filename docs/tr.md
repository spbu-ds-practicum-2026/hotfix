# Техническое решение проекта «Verdict»

## Введение

### Краткое описание

«Verdict» — учебный проект, реализующий прототип распределённой системы для приёма, проверки и отображения результатов решений участников соревнования по программированию в формате ICPC.

Система позволяет участнику зарегистрироваться в контесте, просматривать задачи, отправлять исходный код на проверку, получать вердикт и видеть текущее положение команды в турнирной таблице.

Проверка решений выполняется асинхронно несколькими экземплярами Judge Worker. Для выполнения пользовательского кода используется внешний self-hosted сервис Judge0. Система должна корректно работать при отказе отдельных воркеров и не должна создавать несколько результатов для одной и той же посылки.

### Цель проекта

Реализовать прототип распределённой системы приёма и проверки посылок участников соревнования по программированию с поддержкой отказоустойчивости, масштабирования и корректной обработки повторных сообщений.

### Задачи

- реализовать приём и автоматическую проверку посылок участников;
- организовать асинхронную обработку решений;
- обеспечить отказоустойчивость и масштабирование системы;
- обеспечить корректную обработку повторных сообщений и операций;
- реализовать расчёт ICPC scoring и режим freeze;
- реализовать пользовательский интерфейс и тестирование основных сценариев.

## Глоссарий

| Термин | Определение |
|---|---|
| **Участник** | Пользователь, зарегистрированный в контесте. |
| **Команда** | Группа участников, выступающая в контесте и имеющая общий результат. |
| **Контест** | Соревнование по программированию с набором задач и ограниченным временем проведения. |
| **Задача** | Программная задача контеста, для которой участник отправляет решение. |
| **Посылка (Submission)** | Отправленный участником исходный код для решения конкретной задачи. |
| **submissionId** | Уникальный идентификатор посылки, используемый для хранения и идемпотентной обработки. |
| **Вердикт** | Результат проверки посылки: `OK`, `WA`, `TL`, `ML`, `RE` или `CE`. |
| **API Gateway** | Единая точка входа для клиентских запросов и маршрутизации их к сервисам. |
| **Judge Queue** | Очередь сообщений с задачами на проверку посылок. |
| **Judge Worker** | Экземпляр сервиса, который получает посылку из очереди, запускает её проверку и сохраняет результат. |
| **Checker Adapter** | Компонент, скрывающий детали взаимодействия с Judge0 и преобразующий результат его работы в вердикт системы. |
| **Judge0** | Self-hosted сервис компиляции и запуска программ в изолированной песочнице с ограничениями времени и памяти. |
| **Visibility timeout / lease** | Временная блокировка задачи после получения воркером: пока lease активен, задача не выдаётся другим воркерам; после истечения срока невыполненная задача возвращается в очередь. |
| **At-least-once** | Семантика доставки, при которой сообщение доставляется как минимум один раз, поэтому возможны повторные доставки. |
| **Идемпотентность** | Свойство повторной обработки одной посылки, при котором не создаётся второй логический результат для того же `submissionId`. |
| **Дедупликация** | Обнаружение и игнорирование повторно доставленного события по уникальному идентификатору. |
| **Шард** | Независимый сегмент данных Submissions DB. |
| **Consistent hashing** | Способ распределения ключей по узлам хеш-кольца, позволяющий при изменении числа узлов перераспределять только часть ключей. |
| **Мастер** | Реплика шарда, принимающая операции записи. |
| **Реплика** | Копия данных шарда, используемая для отказоустойчивости. |
| **Failover** | Переключение работы с отказавшего мастера на доступную реплику. |
| **Fencing** | Изоляция старого мастера после failover, предотвращающая его дальнейшие записи и split-brain. |
| **ICPC scoring** | Правила подсчёта результата команды на основе решённых задач, количества неправильных попыток и штрафного времени. |
| **Freeze** | Режим контеста, при котором публичная турнирная таблица перестаёт обновляться, хотя внутренняя обработка результатов продолжается. |
| **Eventual consistency** | Модель согласованности, при которой при отсутствии новых изменений представления системы со временем сходятся к одному состоянию. |

## Функциональные требования

Система должна предоставлять следующие функции:

1. Создание и просмотр контестов.
2. Добавление задач и регистрация участников в контесте.
3. Отправка решений и их автоматическая проверка.
4. Просмотр статуса и вердикта отправленных решений.
5. Расчёт и обновление турнирной таблицы по правилам ICPC.
6. Просмотр standings с учётом режима freeze.
7. Просмотр состояния и итогов контеста.

### Ограничения на предметную область

1. Решения проверяются автоматически через Judge0.


## Нефункциональные требования

- **Доступность:** 99.9%.
- **Масштабируемость:** возможность горизонтального увеличения числа Judge Worker без изменения логики Submission Service.
- **Время отклика:** отправка решения и постановка в очередь - ≤ 200 мс в условиях локальной сети.
- **Отказоустойчивость:** система должна продолжать работу при сбое Worker или мастера шарда; недоступность определяется по timeout, lease и health-check; при отказе мастера выполняется failover на реплику.
- **Доставка событий:** семантика at-least-once; повторная доставка события не приводит к повторному учёту результата.
- **Идемпотентность:** повторная обработка одной посылки по `submissionId` не создаёт дубликатов.
- **Консистентность:** состояние посылки однозначно связано с `submissionId`; standings может временно отставать от Submissions DB, но при отсутствии новых событий сходится к актуальному состоянию.
- **Безопасность:** пользовательский код выполняется в изолированной песочнице Judge0.


## Пользовательские сценарии

### Сценарий: отправка решения

1. Участник выбирает контест и задачу и отправляет исходный код.
2. Система создаёт уникальный `submissionId` и сохраняет посылку со статусом `queued`.
3. Посылка попадает в очередь на проверку.
4. Участник получает `submissionId` и статус посылки.

### Сценарий: проверка решения

1. Judge Worker получает посылку из очереди.
2. Worker передаёт код в Judge0 через Checker Adapter.
3. Judge0 компилирует и выполняет решение.
4. Система сохраняет полученный вердикт по `submissionId`.
5. Standings Service обновляет результат команды.


### Сценарий: freeze турнирной таблицы

1. Контест переходит в режим freeze.
2. Standings Service продолжает обновлять внутреннее состояние таблицы.
3. Участникам возвращается snapshot standings, созданный в начале freeze.
4. После окончания freeze отображается актуальное состояние таблицы.
